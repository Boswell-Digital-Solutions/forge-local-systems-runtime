## The cost sync worker lost rows in two cases and reported success (Closed in the local branch 2026-10-13, not pushed) — FLS-COST-SYNC-LOST-ROWS-20261013

- **Location**: `cost_sync/worker.py`, `scripts/run_cost_sync_worker.py`.
- **Case A, reproduced on `c123d0e`:** when an earlier row failed its local write and a later row succeeded, the checkpoint (`max(created_at)` in `cost_sync.seen`) moved past the earlier row. The next pass asked the cloud only for rows from the checkpoint onward, so the earlier row was **never retried**. Evidence: run 1 mirrored `c2` and failed `c1`; run 2 fetched 1 row and did not recover `c1`.
- **Case C, reproduced on `c123d0e`:** when a window held more rows than the safety bound (`_MAX_OFFSET`), the page walk stopped, the worker mirrored the newest rows it had, and the checkpoint moved past the OLDEST rows it never saw. Evidence: 8 cloud rows, 6 mirrored, `SyncResult` showed `synced=6` with no sign of incompleteness, and the 2 oldest rows were missing forever.
- **Also found:** the runner committed once after the whole pass and rolled back on any exception, so a crash mid-pass discarded the dedup records of every row already posted and the next pass posted them all again.
- **Fix (branch):** time windows, oldest first, with a stop at the first row that cannot be mirrored; a pass is `complete` only if every listing matched the cloud's `total`; the dedup record is committed after every row; the runner exits non-zero for an incomplete pass. 29 tests, 12 of 12 mutations caught. The evidence scripts and their SHA-256 are in the operator's evidence folder named in the HANDOFF section of 2026-10-13.
- **Not fixed:** a rejected row (a 4xx from the destination) blocks the sync. It is reported and not skipped. A permanent block needs an operator decision.
- **Past loss:** rows that these two cases lost in the past are not recovered by the fix, because the checkpoint is already past them. Whether any were lost is **not known**. A reconciliation against the cloud ledger would show it. Not done.

## The cost sync could lose rows through the cloud paging order, late rows and parallel workers (Mitigated in the local branch, gaps OPEN 2026-10-13) — FLS-COST-SYNC-ORDER-COVERAGE-20261013

- **Location**: `cost_sync/worker.py`; the source is cloud DataForge `list_cost_entries` (`app/api/multi_provider_crud.py`) behind `GET /api/v1/costs/entries`.
- **Cloud paging contract (read from the source, tested on PostgreSQL 16):** `created_at >= since AND created_at <= until`, `total` as a separate `COUNT`, then `ORDER BY created_at DESC OFFSET :offset LIMIT :limit`. The order is **not unique**. `created_at` is `now()` (transaction start), so rows from one transaction tie.
- **Fault 1, equal timestamps across pages (reproduced).** With the real function, a plan change between two page requests returned 1005 rows with 748 unique and 257 never returned. A source that orders ties differently per page does the same in `tests/test_cost_sync_postgres.py`. Sorting the pages the worker holds cannot restore an omitted row. The worker detects the repeat and reports `listing_incomplete`, writes nothing from that window and never reports complete. This is safe. It is not live: if the wrong order repeats on every pass, the sync stays blocked on that window. The block is visible (exit code 1). Fix: DataForge branch `security/cost-ledger-ordering` (`ORDER BY created_at DESC, id DESC`), local, not pushed, not deployed. **OPEN until it is deployed.**
- **Fault 2, a late-visible row (reproduced).** A row can become visible with a `created_at` older than the checkpoint. The old worker started at the checkpoint, so it never listed the row again, and the pass reported complete. **Mitigated:** a pass now starts `FORGE_COST_SYNC_OVERLAP_HOURS` (default 6) before the checkpoint. **Gap, OPEN:** a row that becomes visible more than the overlap late is still lost, and the pass still reports complete. `test_a_late_visible_row_older_than_the_overlap_is_NOT_found...` documents it. The cause of such a row would be a transaction that commits hours after it starts. DataForge sets statement and idle-transaction timeouts, so it is unlikely. It is not proven impossible, and a read replica or a manual backfill with an old `created_at` would also produce it.
- **Proposal for that gap, NOT built:** one `limit=1` read per pass over the whole range gives the cloud `total`. The worker compares it with its own count of ledger markers in the same range, and reports `coverage_mismatch` when the local count is smaller. This is order independent. It needs one more cloud request per pass and an operator action to repair a mismatch older than the overlap.
- **Fault 3, two workers at once (reproduced).** Both workers saw a row as unseen and both wrote it to DataForge-Local, which has no source id. The marker table stayed correct. The ledger at the destination overstated spend. **Mitigated:** a PostgreSQL session advisory lock. The second pass reports `another_pass_running` and exits 1. The lock ends with the connection. It is not reliable behind a transaction-mode pooler; the runtime database is a direct PostgreSQL connection. It does **not** close the crash window in `FLS-COST-SYNC-NOT-EXACTLY-ONCE-20261013`.
- **Fault 4, a sentinel id (found by reading the code, then tested).** The heartbeat row `__sync_heartbeat__` lives in the same table as the ledger markers. A cloud row with that id would read as already mirrored and would be skipped without a message. Cloud ids are UUIDs, so this does not happen today. **Mitigated:** the worker refuses a row with a reserved id (`cloud_entry_malformed`). The table has no database constraint against it. A constraint needs a migration, which is a proposal.
- **Freshness (changed).** Freshness is now coverage. A complete pass records `covered_through` (its scanned-through time) in a second sentinel row. A pass that copied rows and stopped does not move it. **Limit:** this stores one time. It stores no start of the range and no list of confirmed windows. A real coverage record is a table (`cost_sync.coverage`: range start, range end, pass time, listing counts). That is a new storage contract. It is a **proposal, not built**. The second sentinel row uses `synced_at` for a value that is not a sync time, which is a shortcut that the table proposal would remove.
- **Not proven:** the ordering fault was reproduced on the real `list_cost_entries` only with a forced plan change. With one stable plan on a quiet table, 21 page walks gave no fault. A real plan change in production is plausible and not observed. No test runs the worker against the real DataForge HTTP route.
- **Scope**: the worker mitigations are in the local branch `feat/cost-sync-recovery` (not pushed). The ordering fix is in the local DataForge branch above (not pushed). Faults 1 and 2 stay OPEN as stated.

## The cost sync cannot be exactly-once with today's destination (Open 2026-10-13, retained blocker) — FLS-COST-SYNC-NOT-EXACTLY-ONCE-20261013

- **What is wrong:** DataForge Local's `POST /api/v1/costs/record` gives every call a new id and has no source id. If the worker dies after the local write and before the dedup record, the next pass writes that row again. The ledger then overstates spend by that row. Skipping already-seen ids does not prevent this, because the id is recorded only after the write succeeds.
- **What was done:** the window is one row (the dedup record is committed after every row). `tests/test_cost_sync_recovery.py::test_B_...` documents the duplicate with a fake connection. `tests/test_cost_sync_postgres.py::test_B_...` documents it on real PostgreSQL and a real HTTP destination: after the restart `c2` is stored twice and `c1`, whose marker was committed, is stored once. A marker commit after each row does **not** close the window. It makes the window one row. The pass lock (see `FLS-COST-SYNC-ORDER-COVERAGE-20261013`) closes only the variant with two workers at once. The tests are characterizations of a blocker and not a statement that the behavior is acceptable.
- **Exact proposal, NOT authorized, NOT built (a destination contract):** DataForge Local `POST /api/v1/costs/record` accepts an optional `source_entry_id` (UUID); a migration adds a nullable column and a partial unique index on it (`WHERE source_entry_id IS NOT NULL`); the route answers 201 for a new id, 200 with `duplicate: true` for the same id and payload, and 409 for the same id with a different payload; the worker sends the cloud row id. The change is additive and backward compatible. Other writers send null.
- **Rollout effect:** the sync may duplicate a row after a crash. Keep the cost-sync part of the rollout blocked until the contract exists, or until the operator accepts in writing that a crash can add one duplicate row.

- **Closure row (plan of 2026-10-13; records only; nothing implemented).** Owner of the fix: the DataForge Local receiving path (`app/api/cost_ledger_router.py`, `record_cost`), not this worker. A worker-side "already processed" set cannot close the crash window. Exact next change (needs its own approval): nullable `source_namespace` and `source_entry_id` on `cost_ledger`, a partial unique index, a namespace bound to the authenticated source (depends on the DataForge Local identity), receiver rules 201 / 200 original acceptance / 409 conflict, `INSERT ... ON CONFLICT DO NOTHING RETURNING`, no upsert; existing rows keep `NULL` (legacy provenance unresolved, no backfill, no deletion). Worker side: send the cloud row id; keep the case A and case C checkpoint semantics. Evidence and origin: the PostgreSQL case-B test (stored twice: `[c1, c2, c2, c3]`; subagent run). Missing proof: acknowledgment-loss replay, restart, concurrent replay, payload conflict, cross-namespace rejection, legacy `NULL` rows. Rollback: stop sending the identity; keep columns and index; do not relax denial. State: design recommended; not accepted; case B stays BLOCKED. Full row: DataForge proposal section 10.4, Row 4.

## The cost sync worker reads the cloud ledger with no credential, and DataForge will refuse it (Open 2026-10-13) — FLS-COST-SYNC-NO-CREDENTIAL-20261013

- **Location**: `cost_sync/worker.py` (`CostLedgerSyncWorker._fetch_cloud_entries`, `_http_get_json`), run by `scripts/run_cost_sync_worker.py`. Documented in `doc/system/10-ecosystem-integration.md` §10.2.
- **What is wrong**: the worker calls cloud DataForge `GET /api/v1/costs/entries` with a plain `urllib` request and no `Authorization` header. DataForge's route authorization hardening (branch `security/route-authorization-default-deny`, not deployed) classifies that route `legacy_unauthenticated`, which is refused with 403. After the deploy the worker raises `cloud cost read HTTP 403` and mirrors nothing.
- **Effect downstream**: the worker fills DataForge Local's `cost_ledger`. When the worker stops, that table stops growing. DataForge Local keeps answering `200` from its old rows, so a reader sees old cost as current. Forge_Command reads that replica first only when `DATAFORGE_LOCAL_URL` is set where the app starts. The replica has no freshness field (see `dataforge-Local` `DLO-COST-REPLICA-NO-FRESHNESS-20261013`).
- **The worker itself is not silent**: `run_cost_sync_worker.py` rolls back and re-raises, so the process exits non-zero. Whether a cron job or systemd timer runs it on the operator's machine, and whether anyone sees a failed run, is **not verified**.
- **Cause**: the worker predates the hardening. The DataForge branch `security/cost-ledger-scopes` gives `costs:read` to the service `forge_command` only. This worker is a different service, so it has no eligible identity.
- **Status (local branch `feat/cost-sync-recovery`, NOT pushed, NOT merged, NOT deployed):** the worker now sends a cloud read key (`FORGE_COST_SYNC_CLOUD_API_KEY`), and refusals are named with fixed codes. The identity is `forge_local_runtime`, the canonical identity the DataForge registry already holds for this runtime. DataForge's local branch `security/cost-ledger-scopes` lets that identity hold `costs:read` and nothing else. **No key is issued.** Issuing one is an operator step.
- **Still needed before this works in production:** a `costs:read` key for the service `forge_local_runtime` (operator step), the DataForge branch accepted, pushed and deployed (operator steps), and the constitutional documents of this repo (see `FLS-COST-SYNC-OUTSIDE-AUTHORITY-20261013`).
- **Related**: Forge_Command `FC-COSTS-WRITER-UNLISTED-20261013`, inventory row 14.
